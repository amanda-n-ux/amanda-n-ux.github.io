01 — The problem

Intune had never managed a virtual device the way it managed a physical one. Remote desktops existed before Windows 365, but as separate infrastructure with their own setup and tooling — not something that showed up in Intune’s own device list next to a laptop. Windows 365 changed that: Cloud PCs would be first-class Intune devices, governed by the same policies, compliance checks, and update rings as physical hardware, side by side in one console.

That integration was the whole selling point, but it meant provisioning itself had to become a new concept for Intune, not just a new product inside it. Enrolling a physical device meant bringing something that already existed under management; setting up a Cloud PC meant Intune had to create the device first, then manage it the same way — a sequence its admin model had never needed to handle before. Research also surfaced a real, if secondary, discoverability problem: admins confused Windows 365 with Microsoft 365 and Office 365, and treated provisioning as a one-time setup task disconnected from ongoing management.

02 — What I learned first

The team that had originally built Intune’s guided-scenario pattern was gone by the time Cloud PC needed it. Three scenarios — Boot to Cloud, end-to-end setup, and a Windows 365-for-Agents flow internally called NXT — all needed the same underlying pattern, and there was no one left who owned it. I pulled together a PM and engineer from Cloud PC and a PM from the NXT side myself to investigate requirements from scratch, rather than let three teams each reinvent the pattern independently.

The other early finding was about discoverability, not workflow. Surfacing Cloud PC on the console home page at all meant working across Intune design, engineering, and PM on one side and Cloud PC design, engineering, and PM on the other — plus leadership on both sides — just to agree on placement and framing before a single provisioning screen existed.

03 — Exploration

With three guided scenarios in flight at once, the open question was whether each one needed its own wizard.

Ruled out

A separate wizard per scenario

Boot to Cloud, end-to-end setup, and NXT setup were investigated in parallel, and each had enough surface-level difference to justify its own flow on paper. Building three bespoke wizards would have tripled the design and engineering cost for scenarios that overlapped far more than they differed.

Shipped

One flexible wizard, reused

NXT’s requirements were folded into the same wizard shell built for Boot to Cloud, so admins use one coherent guided scenario for related setup work instead of learning a new pattern per scenario. Boot to Cloud shipped first, in CY23H1; the reusable shell is what carried forward afterward.

04 — What shipped

Windows 365 Boot: admins guide end users to sign directly into their Cloud PC from a physical device, extending the life of aging hardware instead of replacing it. It was the first guided scenario to ship, and the wizard shell built for it became the pattern other setup scenarios reused rather than rebuilt.

05 — Tradeoffs I own

The Flex/Frontline assignment model started with a research gap I flagged myself: nothing had tested how admins actually thought about group-based licensing for a shared Cloud PC. I scoped a dedicated study with research and built prototypes from it, then designed the model to support group-level licensing before anyone had asked for it to handle a user with more than one provisioning policy. That extra flexibility cost more upfront design and research work for a case that didn’t exist yet — and it meant the pattern was already in place when assigning multiple provisioning policies to a single user became a real, requested feature later.

Reconciling three guided scenarios into one wizard shell was slower than letting each team build its own. It meant sitting between Cloud PC, Intune, and the NXT team to find the shape that worked for all three, instead of shipping Boot to Cloud alone and calling it done.

06 — Beyond this feature

The “Getting started” pattern I designed to surface Cloud PC’s guided scenarios in context outgrew Cloud PC — Intune’s own team told me directly they wanted to adopt the same strategy for their own onboarding. I also authored the “source of truth” design reference for Windows 365’s general-availability launch: every standard MEM pattern and Azure control used across the release, plus a full accessibility audit that documented every existing WCAG reflow issue — the kind of fit-and-finish work that doesn’t show up in a single feature but shapes how the whole launch holds together.

This body of work was part of what carried me to Principal Designer in late 2023.

07 — What I’d carry forward

When a pattern’s original owners are gone, someone still has to hold the line — I reconstituted stakeholders from scratch rather than let three teams quietly reinvent the same wizard three different ways.

Design the assignment model for the requirement that hasn’t landed yet, not just the one in front of you — the group-licensing pattern paid for itself the moment multi-policy assignment actually shipped.

One flexible pattern, reconciled across teams, beats three bespoke ones shipped faster — the reuse is what survives past the first feature.
